# アーキテクチャ

## 文書の位置づけ

これは[要求仕様](requirements.md)に従う実装の設計ベースラインであり、稼働中のシステム構成図ではありません。実機非依存の処理を先行開発していますが、受信・デコード・表示への結合は未実装です。元の引き継ぎメモにある構成・理由を整理し、実装上欠かせない境界を明示します。実機依存の成立性は[実装計画](implementation-plan.md)の検証ゲートで確認します。

## コンポーネントと依存方向

```text
Windows デスクトップ
  -> 既製仮想ディスプレイドライバー
  -> FFmpeg: 対象画面の取り込み・H.264 圧縮・TCP 接続開始
  -> USB テザリングの IP ネットワーク
  -> Android アプリ: 受信・圧縮映像の復元・デコード・表示
```

Windows は独立した拡張画面を所有し、Android は映像の表示先です。Android アプリは Windows の画面構成を変更せず、FFmpeg やドライバーを制御しません。PC 固有の取り込み・圧縮差は送信環境に閉じ込め、受信アプリを PC ごとに分岐させません。

PC 側の自作常駐アプリは設けません。検証・運用コマンドの文書化は行いますが、独自の送信制御製品は初期スコープに含めません。

## 接続・信頼境界

Fold が待ち受け、PC が接続を開始します。これは PC の受信待ち受けと、それに伴うファイアウォール変更を避ける元資料の方針です。PC 側の送信制限や Android 側の到達性が不要になるという意味ではありません。

USB ケーブルはアクセス制御や暗号化の代わりにはなりません。USB テザリング用の経路と待ち受け範囲を確認し、意図しない Wi-Fi・モバイル側ネットワークへ受信口を公開しません。USB 側だけに制限できることを検証ゲートとし、成立しなければ、認証などを含む設計変更を採択するまで実運用を止めます。現時点では認証導入の方式を決定していません。

同時に有効な送信セッションは 1 つです。別接続が現在の映像やデコーダー状態を上書きしないことを不変条件とします。受信したデータは不正・過大である可能性を前提とし、メモリと待機時間を有限にします。

## 映像の互換境界

FFmpeg から Android へ渡す形式は、音声なしの Annex-B H.264 over TCP をベースラインとします。TCP の読み取り単位、NAL ユニット、圧縮された 1 フレーム相当のアクセスユニットは別物です。受信アプリがこれらを混同しないことを送受信間の互換条件とします。

受信アプリの内部は、通信、映像単位の復元、デコーダー、表示・状態通知の責務に分けます。Android に依存しない映像境界の処理は、実機なしで検証可能にします。キューや未完データは上限を持ち、消費が追いつかない場合に遅延を無制限に蓄積させません。

先行検証の JVM コアはソケット、Android のデコーダー・Surface を所有しません。合成入力での仮契約の検証に限定し、アクセスユニット境界を復元できることと、H.264 の全構文が正しいこと・実機でデコードできることを区別します。仮契約で対応しない入力は推測して受理せず明示的に拒否します。

コアへの操作は単一の所有スレッドで直列化する前提です。セッション終了は保留データと統計を破棄し、解除通知を一度だけ行います。通知を実ソケットの待機解除・デコーダー解放へ接続する責任は将来の Android 結合側にあり、コアのテストだけでその解放を保証しません。

デコードに必要な構成情報と復旧可能な映像開始点をセッションごとに取得します。前セッションの構成情報や未完のデータを再利用しません。送受信のフレーム境界とタイムスタンプの具体的な契約は、P1 の実証結果に基づき実装・テスト側で固定します。元資料の「NAL ごとに投入すればよい」は未検証の仮説として扱います。

取り込み GPU とエンコーダーの整合性は PC 側の責任です。Arm64 / x64 とも、エンコーダー一覧への掲載ではなく、実際に圧縮した映像が共通の受信条件を満たすことを確認します。

## セッションと資源のライフサイクル

受信・デコードは表示用の Surface とアプリの前景ライフサイクルに従います。Surface を持たない状態で表示を続けず、バックグラウンド常駐は行いません。画面点灯の維持も有効な表示状態に限定します。

切断、無通信、破損映像、デコード失敗、Surface 喪失はセッション終了の理由です。接続とデコーダーを解放し、未完データを破棄して、表示可能になったときに新規接続を待ちます。古い処理が終了後の Surface や新しいセッションに書き込まないことを保証します。

USB 経路が失われた場合はエラーを表示し、経路の再確認後に待ち受けを再開します。USB アドレスが変わり得るため、以前のアドレスを固定の識別子としません。終了・再試行はブロック中の受信を解除できる必要があります。

## 可観測性と永続化

adb が使えない状態でも、状態、エラー理由、復旧に必要な操作、実測値をアプリ画面から確認できます。低遅延機能の未対応やエンコーダーの変更を、成功したように隠しません。

受信映像は保存せず、状態と統計値は原則セッション内だけに保持します。運用上の検証結果には映像内容や機密性のある画面を含めません。診断値は測定区間を明確にし、アプリ内処理時間と PC から Fold までの総遅延を区別します。

## 判断記録の扱い

現段階で新しい Accepted ADR は作成しません。元資料の方針を超える重要判断、たとえば伝送形式の変更、認証、バックグラウンド動作の追加は、理由と代替案を確認して ADR に記録し、この文書も更新します。
