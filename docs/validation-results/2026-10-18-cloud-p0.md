## 実行条件

リポジトリとローカル環境を読み取り調査しました。版表示には `java -version`、`gradle --version`、SDK 内の `adb version` を使用し、SDK の版は各パッケージの `source.properties` から確認しました。OS は `uname -srm` と `/etc/os-release`、ネットワークインターフェイス名は `/sys/class/net` で確認しました。

`adb` は版表示だけに使用し、接続・転送・logcat は使用していません。USB テザリングに相当する接続は確認できておらず、ローカルネットワークでの代替疎通も実施していません。ドライバー導入、ネットワーク設定変更、受信ポート公開、映像生成・転送は行っていません。解像度・fps・ビットレートの実測値はありません。

## 制限・気づき

- Android 開発ツールの追加だけでは、Windows の VDD / 取り込み / エンコード、Fold の USB 限定待ち受けの成立性を実証できません。
- エミュレーターや Linux の合成映像で成功しても、P0 の対象実機ゲートを置き換えられません。このため P1 のプロジェクト作成には進んでいません。
- 管理ポリシーは不明であり、許可済みとも禁止とも判定していません。制限回避やセキュリティ設定の無効化は行っていません。

以下は配布元・公式資料の確認であり、インストールや動作の検証結果ではありません。初回の環境調査後、実機非依存の先行検証が承認されました。その実行結果は [P1 独立検証記録](2026-10-18-cloud-p1.md)に分離します。

| 対象 | 文書上確認できたこと | P0 で残る確認 |
| --- | --- | --- |
| IddCx | Microsoft は IDD を UMDF ドライバーとして説明している。[モデル概要](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/indirect-display-driver-model-overview)。[公式サンプル](https://github.com/microsoft/Windows-driver-samples/blob/main/video/IndirectDisplay/IddSampleDriver/IddSampleDriver.vcxproj)に ARM64 ビルド構成がある | サンプルのビルド対応は、第三者配布物の署名・導入成功を保証しない |
| ドライバー署名・許可 | [Driver Store](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/driver-store)は信頼されるカタログ署名と導入権限を要求している | 採用する資産の INF・CAT・対象バイナリー・署名と各 PC の導入許可。署名済みという表明を動作保証にしない |
| VDD 候補 | VirtualDrivers の [25.7.23](https://github.com/VirtualDrivers/Virtual-Display-Driver/releases/tag/25.7.23)には署名済みドライバーの表明と ARM64 資産がある。一方、[同タグ README](https://github.com/VirtualDrivers/Virtual-Display-Driver/blob/25.7.23/README.md)は Windows 11 24H2 以降の ARM64 でテスト署名が必要な場合があると明記している | **通常のセキュリティ設定で導入できるとは未確認。** 必要ならこの候補の採用を保留し、管理者確認・許可された代替候補の評価へ戻る。テスト署名や Secure Boot の変更で回避しない |
| カスタム解像度 | [25.7.23 の設定例](https://github.com/VirtualDrivers/Virtual-Display-Driver/blob/25.7.23/Virtual%20Display%20Driver%20(HDR)/vdd_settings.xml)に幅・高さ・リフレッシュレートの形式がある | 2184×1968 が当該版で登録・列挙・適用・取り込みできるかは未確認 |
| 取り込み・変換 | FFmpeg の [ddagrab](https://ffmpeg.org/ffmpeg-filters.html#ddagrab) は D3D11 ハードウェアフレームを出力する。ソフトウェア処理には明示的な [hwdownload](https://ffmpeg.org/ffmpeg-filters.html#hwdownload) が必要。[hwmap](https://ffmpeg.org/ffmpeg-filters.html#hwmap) も互換デバイスを要する | 採用ビルドのフィルター有無、取得・変換・圧縮の GPU 整合、転送負荷。`video_size` は画面モード設定の代替ではなく、クロップとの区別が必要 |
| Desktop Duplication | Microsoft の [DuplicateOutput](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput) は出力が接続されたアダプターの D3D デバイスを要求し、セキュアデスクトップ等の制約を挙げている | VDD の画面列挙と実際の取得成功を別々に試験。権限・ロック・モード変更時の失敗を設定回避で解決しない |

| TCP | [FFmpeg TCP](https://ffmpeg.org/ffmpeg-protocols.html#tcp) の `listen` は既定で 0、`local_addr` で送信元 IP を指定可能 | FFmpeg が接続開始側になる構成とは整合するが、USB 実経路や自動再接続の成立は未確認 |

FFmpeg の調査では公式の現行文書に加え、[n7.1.1 の文書ソース](https://github.com/FFmpeg/FFmpeg/tree/n7.1.1/doc)を照合しました。採用する Windows 配布ビルドに同じ機能が含まれるとは断定しません。完成した Windows 送信コマンドは追加していません。

Android Developers 本文はこの環境では名前解決エラーで直接取得できませんでした。[AGP 8.7 の公式リリースノート](https://developer.android.com/build/releases/past-releases/agp-8-7-0-release-notes)、[低遅延 API](https://developer.android.com/reference/android/media/MediaCodecInfo.CodecCapabilities#FEATURE_LowLatency)、[LAN 権限](https://developer.android.com/privacy-and-security/local-network-permission)は、実機環境で OS・targetSdk・選択デコーダーの条件とともに再確認が必要です。API の存在だけで Fold の対応を断定しません。

JetBrains の[公式ドキュメントソース](https://github.com/JetBrains/kotlin-web-site/blob/master/docs/topics/gradle/gradle-configure-project.md)では、Kotlin 2.1.20〜2.1.21 の fully supported 範囲は Gradle 7.6.3〜8.12.1、AGP 7.3.1〜8.7.2 です。このため、先行検証は AGP 8.9.2 ではなく 8.7.2 を採用しています。ただし、Android 側の依存取得・ビルドが成立した証拠ではありません。実際の採用版・ビルド結果は P1 記録を正とします。

## 実機環境への引き継ぎ

次の項目は**未実施の確認事項**であり、検証済みの操作手順ではありません。[P0 の作業と完了条件](../implementation-plan.md#p0-環境成立性の確認)、[初回準備](../operations.md#初回準備)に従い再開してください。

1. Windows Arm64、AMD CPU 搭載 Windows x64、同じ Fold7、USB データケーブルを用意します。各 PC と Fold で USB テザリング・APK・署名済み既製ドライバー導入の許可を確認します（Q01）。禁止なら中止します。
2. 各 PC の OS、GPU とドライバー、VDD / FFmpeg の取得元と版を記録します。識別用の非機密画像で拡張画面の取り込みと 2184×1968 の H.264 生成を確認し、実際のエンコーダーと出力条件を記録します（Q02・Q03、T01・T12 の P0 範囲）。元資料のコマンドは未検証のままです。
3. 許可された検証用アプリ等で、開発者モード無効時の導入済みアプリ起動と USB 側アドレスへの限定待ち受けを確認します。PC からの接続、許可された他インターフェイスへの非公開、USB 再接続時のアドレス変化を記録します（Q04、T02・T03 の P0 範囲）。全インターフェイス待ち受けで代替しません。
4. 通常回線あり・なしの実経路と携帯回線利用の可能性を確認し、変更した設定の復元も記録します（Q09、T11）。モバイル通信を許容できず経路が不明なら開始しません。
5. 性能基準案の採否を利用者と合意し、変更時は理由を残します（Q07）。両 PC の P0 結果を環境別に記録し、完了条件を満たしてから P1 へ進みます。

P0 のファイル生成・疎通確認は P4 の全試験成功を意味しません。P1 では両 PC の非機密な出力サンプルと圧縮条件を使って映像契約を実証し、SDK・JDK・Gradle の公式な互換性を確認してビルド基盤を固定します。
