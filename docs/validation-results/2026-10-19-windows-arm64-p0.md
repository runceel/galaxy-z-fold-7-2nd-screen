### 合成入力のコマンドと観測

次は今回実行した圧縮条件です。`$Ffmpeg` は上記版の実行ファイルの絶対パス、出力先の変数は作業専用ファイルの絶対パスを表します。**Windows の実画面送信コマンドではありません。**

```powershell
& $Ffmpeg -hide_banner -loglevel info -nostdin -y -f lavfi -i testsrc2=size=2184x1968:rate=60 -frames:v 60 -an -c:v h264_mf -hw_encoding 1 -pix_fmt nv12 -bf 0 -g 60 -b:v 30M -f h264 $HardwareOutput
& $Ffmpeg -hide_banner -loglevel info -nostdin -y -f lavfi -i testsrc2=size=2184x1968:rate=60 -frames:v 60 -an -c:v libx264 -preset ultrafast -tune zerolatency -pix_fmt yuv420p -bf 0 -g 60 -b:v 30M -x264-params aud=1:repeat-headers=1:slices=2 -f h264 $SoftwareOutput
```

HW 試験に失敗した場合の自動的なソフトウェアへの切り替えは行っていません。両試験は別プロセスで並行実行したため、速度比較用の測定ではありません。

| 観測 | h264_mf（HW を要求） | libx264（ソフトウェア） |
| --- | --- | --- |
| プロファイル・レベル | Constrained Baseline、5.2 | Constrained Baseline、5.2 |
| 出力寸法・画素形式 | 2184×1968、yuv420p | 2184×1968、yuv420p |
| B フレーム | ffprobe の has_b_frames は 0 | ffprobe の has_b_frames は 0 |
| ffprobe の読み取りフレーム数 | 60 | 60 |
| 全フレームのソフトウェアデコード | `-err_detect explode` で終了コード 0 | 同左 |
| ファイル内の AUD / SPS / PPS | 60 / 1 / 1 | 60 / 1 / 1 |
| IDR の NAL 数 | 1 | 12（スライス数とピクチャ数を混同しない） |
| 最大 NAL サイズ（開始コードを除外） | 149,630 bytes | 52,316 bytes |
| AUD 区切りの最大サイズ（開始コードを 4 bytes に正規化） | 149,678 bytes | 181,192 bytes |
| プロセスの壁時計時間 | 897ms | 455ms |
| FFmpeg 最終ログの speed | 1.32x | 3.76x |

NAL と AUD 区切りのサイズは、この有限の合成ファイルの開始コードを走査した値です。全 H.264 構文、ピクチャ所属、SPS/PPS とスライスの整合、実機デコーダー互換性を検証したものではありません。`slices=2` の指定でも対象サイズでは複数スライスが生成されており、指定値だけから実数を仮定しません。

両ファイルの raw H.264 に対し ffprobe は `r_frame_rate=120/1`、`avg_frame_rate=25/1` と報告しました。生成指定の 60fps と異なる推定値であり、これらを実表示 fps や性能の判定に使いません。1 秒相当の合成入力を短時間処理できたことは、実画面取り込み・USB 転送・Fold 表示を含む 60fps の達成や連続稼働を意味しません。

既存の L06 は JDK 17 と上記 FFmpeg をそれぞれ `JAVA_HOME`、`FFMPEG` に設定し、次で実行しました。Android SDK は指定していません。対象は既存の 64×64 合成入力であり、上の対象解像度の HW ファイルをコアに投入したテストではありません。

```powershell
.\gradlew.bat -p core ffmpegIntegrationTest --offline --no-daemon --configuration-cache --console=plain
```

## 後続の UAC 承認と導入失敗

利用者の明示的な許可後、署名を再確認した VDD Control を `RunAs` で管理者起動しました。この実行環境から導入 UI を確認・操作できなかったため、利用者が開いた画面で映像ドライバーの通常導入を実行しました。利用者が提示したログは、Arm64 PC に対して Control が `Architecture: x86` と `SignedDrivers\x86\VDD` を選び、devcon が終了コード 2 で失敗したことを示しています。

当該 INF を読み取り確認すると、`x86` と名付けられたフォルダーの INF は `NTamd64`、別の `ARM64` フォルダーの INF は `NTARM64` を対象としていました。SetupAPI の該当ログも `0xe0000228: There are no compatible drivers for this device` と `No devices were updated` を報告しています。この初回の失敗と、以下の正しい Arm64 INF に対する署名検証の失敗は分離します。

導入ツールは `C:\VirtualDisplayDriver\vdd_settings.xml` とルートデバイス 1 個を作成してから失敗しています。対象デバイスの Hardware ID は VDD の INF と一致しますが、DriverInfPath・DriverVersion・DriverProvider は未設定で、Driver Store に VDD のパッケージは追加されていません。PnP の Status が OK / ProblemCode 0 でも、ドライバー導入・表示成功の証拠にはしません。コピーされた XML には 2184×1968 がなく、未構成デバイスと設定フォルダーの処理は残っています。

### 正しい Arm64 INF を明示した再試行と停止点

改めて利用者の UAC 実行許可を得て、Windows 標準のネイティブ PnPUtil に、同梱の `SignedDrivers\ARM64\VDD\MttVDD.inf` を明示して `/add-driver` と `/install` を実行しました。実行前に CAT の Authenticode が引き続き Valid で、INF が NTARM64 を対象とすることを確認しました。

PnPUtil は終了コード `-2146762487`（`0x800B0109`）で失敗しました。SetupAPI は、信頼プロバイダーが信頼しないルート証明書で証明書チェーンが終端したこと、Code Integrity が有効なためドライバーパッケージの署名検証と Driver Store への取り込みが失敗したことを明示しています。通常の Authenticode の Valid と、ドライバーパッケージとしての受け入れは異なります。WDF schema 2.23 / 要求 2.25 の警告もありましたが、今回の停止原因として確定したのは署名検証の拒否です。

利用者からもう一度インストールを試すよう依頼を受け、設定と配布物を変更せず同じ Arm64 INF による通常導入を 1 回再実行しました。これも同じ `0x800B0109` で失敗し、SetupAPI に同じ Code Integrity・署名検証の拒否を確認しました。両試行後とも対象デバイスのドライバー情報は未設定でした。

ここでこの候補の導入を停止します。証明書ストアへの追加、テスト署名、セキュアブート・Code Integrity の無効化、INF / CAT の編集、管理制限の回避は実施していません。現構成で採用できる VDD は確定しておらず、通常の署名条件で受け入れられる Arm64 対応候補の評価、または管理者・配布元への確認が必要です。

導入失敗時に作られたルートデバイスの削除は別の UAC 操作として許可を求めましたが、利用者は導入再試行を選んだため削除していません。`C:\VirtualDisplayDriver\vdd_settings.xml` と、ドライバー未適用のデバイス 1 個が残っています。新しい仮想モニターは確認できていません。

後続の Screen API では主画面 `(0,0,2880,1920)`、副画面 `(-595,-2880,5120,2880)` と、初回とは異なる座標・寸法を観測しました。DPI コンテキスト等の影響は未調査であり、配置が不変だったと断定する証拠にも、設定を復元するための確定値にも使いません。初回の値を根拠に画面設定を自動で戻す操作は行っていません。

spacedesk の[公式構成説明](https://manual.spacedesk.net/INTRODUCTIONANDSETUP.html)では、Primary Machine の DRIVER にネットワーク表示サーバーとドライバーが含まれ、Secondary Machine は専用 VIEWER を使います。[Connection Close Delay](https://manual.spacedesk.net/spacedeskConnectionCloseDelay.html)には切断後の画面を PC の再起動まで保持する設定がありますが、Viewer なしの初回作成、再起動後の復元、サーバーの公開範囲は検証していません。保持機能があることを、現在の「既製 VDD + FFmpeg / 自作 Android アプリ」の構成でそのまま使える証拠にはしません。[Viewer のライセンス](https://www.spacedesk.net/licensing/)も用途に応じた確認が必要です。

この調査では採用候補の確定、構成変更、新たな UAC 操作は行っていません。Q01・Q02 は未解決のままです。追加のサーバー・Viewer を伴う導入検証に進む場合は、評価範囲とライセンスを確認し、UAC 操作の前に改めて利用者の許可を得ます。以前の失敗で残ったデバイスと設定ファイルも変更していません。

## 後続の spacedesk 導入と受信待ち受けの停止

MSI を実行せず読み取り専用で開き、Summary Template が `Arm64;1033`、ProductVersion が `2.2.33.0` であることを確認しました。埋め込み CAB の読み取り・展開だけを行い、導入アクションは実行せず、次を確認しました。

| ドライバー | INF の版 | Arm64 実体 | カタログの署名 |
| --- | --- | --- | --- |
| spacedesk Display | 10.2.398.176、2025-06-02 | INF に ntarm64 / Windows build 22000 以降、表示 DLL は PE Machine 0xAA64 | Valid、Microsoft Windows Hardware Compatibility Publisher |
| spacedesk virtual Bus | 1.0.491.50、2026-02-16 | INF に ntarm64 / Windows build 22000 以降、SYS は PE Machine 0xAA64 | Valid、Microsoft Windows Hardware Compatibility Publisher |

DLL / SYS 自体の Authenticode も Valid、署名者は Datronicsoft Inc. でした。MSI には単一の製品 Feature と、サーバー・サービス起動、USB・入力・音声・映像キャプチャー等の導入アクションがありました。ファイアウォール許可アクションは新規導入時のチェックに連動し、そのチェックの既定値は有効でした。アクションの存在だけで、全ペイロードの適用完了とは判断しません。

利用者に変更範囲を示し、UAC 付き通常セットアップの起動許可を得ました。直前に MSI のハッシュ・署名を再確認し、spacedesk に該当する既存アプリ・サービス・ファイアウォールルール・適用済みドライバーは検出しませんでした。利用条件の確認と UI 操作は利用者が行い、再起動は抑止しました。

利用者の完了申告後、MSI の `Installation completed successfully` と終了コード 0、Display INF の Driver Store 登録（Attested、Microsoft Windows Hardware Compatibility Publisher）、仮想バスと Android Control の署名済みドライバー適用を確認しました。一方、Screen API の画面数は既存の 2 画面のままで、対象拡張画面の生成や表示ドライバーの対象デバイスへの適用・表示成功は確認していません。

### ファイアウォール許可と対処

セットアップでは通信許可が有効なまま導入されました。利用者からの申告と実機の両方で確認し、次を観測しました。

- `spacedeskService` は自動起動・実行中。TCP 28252 は `0.0.0.0` で待ち受け、同サービスの UDP 28252 も検出した。
- 同サービス EXE を対象とする受信 Allow ルールが 1 件、全プロファイルで有効だった。他機器からの到達試験やネットワーク走査はしていない。

改めて利用者から UAC 操作の許可を得て、実行ファイルの一致を確認したサービスだけを停止し、作成された受信許可ルール 1 件だけを PersistentStore で無効化しました。ActiveStore でも無効を確認し、対象サービスの TCP / UDP 待ち受けは消失しました。Windows ファイアウォールのプロファイル有効状態は操作前後で一致し、他のルール・証明書ストア・セキュリティ設定は変更していません。

終了時はサービス Stopped / ProcessId 0、当該ルール Disabled です。**サービスの起動種別は Auto のまま**で、次回 PC 起動時にサービスが再開する可能性があります。自動起動設定の変更・再起動・アンインストールは実施していません。以前の VDD の未構成デバイスと設定ファイルも残したままです。

今回確認できたのは通常署名条件でのパッケージ導入と、発生した待ち受けの停止までです。PC の受信待ち受けを避ける設計ベースラインに対して、専用サーバーなしでの画面生成・維持・復元は未確認です。サービスの再開や Viewer 接続には進まず、採用・構成変更・T01〜T12 の合格とは扱いません。
