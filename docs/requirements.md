# 要求仕様

## 状態と根拠

2026-10-18 時点。[開発引き継ぎメモ](../fold7-submonitor-handover.md)を元に整理した要求仕様です。P1 の実機非依存部分を先行開発していますが、Windows / Fold 実機の成立性は未確認です。入力資料の要件と、その実現手段についての仮説を区別します。

## 目的と対象

個人利用の Galaxy Z Fold7 を Windows の拡張ディスプレイとして使用します。既存画面の単なるミラーリングではなく、Windows から独立したモニターとして認識されることが必要です。

| ID | 要求 | 判定の要点 |
| --- | --- | --- |
| R01 | Windows Arm64 と AMD CPU 搭載 Windows x64 に対応する | 同じ Android アプリを使用し、PC ごとに送信環境を検証する |
| R02 | Fold の開いたメイン画面、2184×1968 を対象とする | 仮想ディスプレイから表示まで対象解像度を保つ |
| R03 | 実運用の映像経路は USB テザリングに限定する | Wi-Fi や adb の転送を実運用の前提としない |
| R04 | 開発者モードが無効でも導入済みアプリを使用できる | 起動、接続、再接続、診断に adb / logcat を必須としない |
| R05 | 表示専用とする | タッチなどの入力を PC に送らない。TCP 自体の双方向制御通信は排除しない |
| R06 | PC を接続開始側、Fold を待ち受け側とする | Fold の USB 側アドレスを環境ごとに確認する |
| R07 | 映像を全画面表示し、向きを固定し、表示中は画面点灯を維持する | 映像に不必要な変形を加えず、点灯維持を表示セッション外へ持ち越さない |
| R08 | アプリ内で状態と診断情報を確認できる | 待機・接続・エラー、受信量、表示 fps、アプリ内処理時間を区別して表示する |
| R09 | 切断後に資源を解放して再接続できる | FFmpeg を再起動すれば、アプリの再インストールや再起動なしで再表示できる |
| R10 | 両 PC で 2184×1968 / 60fps の運用成立を目標とする | 設定値ではなく、実測 fps、遅延、発熱と安定性を確認する |
| R11 | 既製の仮想ディスプレイドライバーと FFmpeg を利用する | 自作の製品コードは Android アプリに限定する |
| R12 | 端末・PC の管理ポリシーを順守する | 禁止される場合は中止し、制限回避やセキュアブート無効化を行わない |

R08 は元資料の「受信 fps、デコード遅延」を測定可能な形に具体化しています。バイト受信だけから fps は分かりません。圧縮フレーム単位の入力件数と表示用に解放した出力件数を区別し、アプリ内処理時間を画面間の総遅延と呼ばないことが必要です。

## 初期対象外

- タッチ入力、音声、クリップボードなどの付加通信。
- 開閉追従、カバー画面、テーブルトップ姿勢、解像度の動的切り替え。
- Wi-Fi、インターネット越しの接続、複数送信元の同時表示。
- 自作ドライバー、配布用インストーラー、多機種対応、常駐サービス。
- 120fps と自動的な画質・ビットレート調整。60fps 成立後の別計画とする。

初期の 30fps は疎通・切り分け用です。60fps を満たした扱いにはしません。

## 実装前に解消する事項

| ID | 未確定事項 | 確認段階・対応 |
| --- | --- | --- |
| Q01 | USB テザリング、APK 導入、外部ドライバー導入が許可されるか | P0。禁止の場合は進めず、管理者確認または許可された環境へ切り替える |
| Q02 | 各 PC で VDD、対象解像度、Desktop Duplication が成立するか | P0。配布版の署名・対応アーキテクチャ・必要権限も確認する |
| Q03 | 各 PC の GPU、FFmpeg ビルド、利用可能なエンコーダー | P0。CPU メーカーから GPU を推定しない |
| Q04 | Fold の受信ポートへ USB 経由で到達でき、待ち受けを USB 側へ制限できるか | P0。USB 以外から到達する可能性を評価し、制限できなければ設計を再検討する |
| Q05 | 受信 H.264 と MediaCodec の互換性、低遅延機能の対応 | P1・P2・P4。未対応を画面に明示し、通常デコードでも実測する |
| Q06 | 全画面時の実表示領域と向き、縦横比の扱い | P2・P4。引き伸ばさず、必要な余白とシステム UI の影響を確認する |
| Q07 | 許容する総遅延、fps の許容差、連続使用時間 | P0 で基準案を採否判断。未承認値を確定要件にしない |
| Q08 | Android の SDK・JDK・Gradle・依存バージョン | P1。採用時点で公式の互換性を確認し、固定・再現可能にする |
| Q09 | テザリング中の PC インターネット経路 | P0・P4。メトリックだけでモバイル通信を完全に防げるとは扱わない |

## 入力資料の読み替え

「USB 有線なら認証不要」「自分専用なら署名の考慮不要」「アプリは 100〜200 行」は成立性を保証する要件ではありません。USB テザリングはネットワーク接続なのでアクセス範囲を確認し、既製ドライバーと APK の署名・導入条件も確認します。アプリの規模は、復旧処理とテストを設計してから見積もります。

技術候補、コマンド、OS・ツールの対応状況は元資料の調査時点の仮説です。実装着手時に実物と公式資料で確認し、結果を記録します。
