# 実装計画

## 方針

Windows 側の成立性を先に確かめ、次に H.264 と Android デコーダーの互換性を小さく実証します。その後、復旧・診断を含むアプリを完成させ、両 PC と Fold 実機で受け入れを行います。P0 は環境調査に着手しましたが未完了、P1 は実機非依存部分に着手、P2〜P5 は未着手です。

参照: [要求仕様](requirements.md)、[アーキテクチャ](architecture.md)、[検証計画](validation-plan.md)、[セットアップ・運用](operations.md)。

## 現在の阻害要因

2026-10-18 の[クラウド環境調査](validation-results/2026-10-18-cloud-p0.md)では Android 開発ツールの存在を確認しましたが、対象の Windows Arm64 / AMD CPU 搭載 x64 PC と Fold7 を利用できず、P0 の成立性を検証できていません。Q01〜Q04、Q07、Q09 は未解決です。

対象実機を利用できる環境で P0 を再開し、環境別の検証結果を揃えてから P1 の実機依存部分へ進みます。開発ツールの存在は、Android ビルドの再現性や P0 完了の証拠にはしません。具体的な実機引き継ぎ項目は上記の調査記録を参照してください。

先行する P1 の実行結果と制限は[クラウド独立検証記録](validation-results/2026-10-18-cloud-p1.md)へ記録します。P0 の Q01〜Q04・Q07・Q09 はこの検証では解消しません。

2026-10-19 の [Windows Arm64 開発環境での独立検証](validation-results/2026-10-19-windows-arm64-p1.md)では Google Maven の依存解決、Android Lint、debug APK 生成・内容確認まで進みました。後続で、利用者が導入を許可した接続中の Fold7（Android 16）へ開発用 adb で導入し、説明画面の起動・再起動を確認しました。これは P0 の APK 導入確認の一部であり、開発者モード無効時の運用、P0 の残る実機確認と P1 の映像契約確定は引き続き未完了です。

同日の [Windows Arm64 P0 調査](validation-results/2026-10-19-windows-arm64-p0.md)では Adreno X1-85 GPU と、合成入力に対する Qualcomm の HW H.264 圧縮を確認しました。VDD Control の通常導入は異なるアーキテクチャの選択で失敗し、正しい Arm64 INF を PnPUtil に明示した試行も 2 回とも署名検証（0x800B0109）で拒否されました。セキュリティ設定は緩和せず、この版の導入は停止しています。通常の署名条件で導入できる候補の確認と作成済みデバイスの処理、拡張画面の取り込み、USB 経路、AMD x64 PC、Q07 の合意は残っており、P0 は完了していません。

代替候補の調査と後続の導入試験も同記録に追記しました。spacedesk は利用者の UAC 許可と UI 操作により通常署名条件でのパッケージ導入を確認しましたが、PC の受信待ち受けが発生したため、別途許可を得て当該許可ルールを無効化しサービスを停止しています。専用サーバー・Viewer に依存しない画面の作成・維持・復元は未確認で、現設計への採用は未決定です。自動起動設定等の残留状態は同記録を参照し、追加のサーバーを前提とする構成へ無断で置き換えません。

## 依存関係

```text
P0 環境・成立性
  -> P1 プロジェクトと映像契約
      -> P2 最小受信表示
          -> P3 復旧・診断・資源管理
              -> P4 両 PC と実機の結合・受け入れ
                  -> P5 再現可能な個人運用
```

P0 の禁止事項を未解決のまま実機への導入・通信を実施しません。2026-10-18 の先行検証の合意により、P1 のうち次の実機非依存部分だけは P0 と並行できます。

- 固定したツールチェーンでの Android ビルド、単体テスト、Lint、APK 生成。APK は開発基盤確認用であり、受信表示機能は含めない。
- JVM 上の映像解析、セッション制御、診断値の実装と単体テスト。ソケット・MediaCodec・Surface との結合は含めない。
- 合成 H.264 入力の解析。送信条件は仮契約として扱い、実 PC の出力・Fold の互換性を代替しない。

この先行検証で P0・P1 の完了や T01〜T12 の実機合格を宣言しません。P1 の映像契約の確定には P0 完了後の両 PC の出力と Android デコーダーの確認が必要で、P2 以降の前提は変更しません。ソフトウェア単体テストは P1 から各段階で追加し、最後にまとめて書く方式にはしません。エミュレーターは補助であり、実機の代替ゲートにはしません。

## P0: 環境・成立性の確認

**目的:** 自作アプリ以前の阻害要因を解消する。対象: R01〜R04、R10〜R12、Q01〜Q04、Q07、Q09。

作業:

- 管理ポリシー、APK 導入と署名、USB テザリング、既製ドライバー導入の可否を確認する。導入済み APK が開発者モード無効でも起動できるかを、許可された検証用アプリ等で確認する。
- 両 PC の OS、CPU アーキテクチャ、GPU、ドライバーと FFmpeg の版を記録する。VDD の取得元、署名、2184×1968 の登録方法を確認する。
- 拡張画面を作り、対象画面の識別と取り込みを確認する。短い H.264 ファイルを保存し、画面内容、解像度、fps を確認する。
- エンコーダーを短時間実行し、HW 利用可否を確認する。AMD CPU でも GPU は実物を調べ、AMF / NVENC / MF / ソフトウェアの候補を選ぶ。
- USB アダプター、Fold のアドレス、実際の到達経路とルーティングを確認する。ポート 5000 は元資料の候補とし、競合も確認する。
- 待ち受け範囲を USB 側へ制限できるかを小さな実験で確認する。無条件の全インターフェイス公開で先へ進めない。
- 許容遅延と安定性の基準案を確認する。端末が手元にない項目は「未確認」とし、成立済みと扱わない。

**成果物:** 環境別の検証結果、採用可能な FFmpeg 候補コマンド、ブロッカー一覧。

**完了条件:** 両 PC で拡張画面の取り込みと対象解像度の H.264 生成を確認し、管理ポリシーと USB 限定待ち受けの阻害要因を解消している。60fps 未達は結果に残し、達成する見通しを判断する。成立しない PC は対応済みとせず、計画見直しの対象とする。

## P1: Android 開発基盤と映像契約の実証

**前提:** 実機依存部分は P0 完了。実機非依存部分だけは上記の例外範囲で先行可能。対象: R01、R02、R08、Q05、Q08。

作業:

- Kotlin の Android アプリとテスト基盤を作る。SDK・JDK・Gradle の互換性を確認し、Gradle Wrapper と依存バージョンを固定する。UI は表示用 Surface と状態表示を中心とした最小構成にする。
- 最小 Android バージョン、ネットワーク権限、採用 SDK で必要なローカルネットワークアクセス条件を確認する。不要な権限は要求しない。
- P0 の出力について、プロファイル、ピクセル形式、B フレーム、構成情報、キーフレーム間隔を確認する。再接続ごとに必要な情報が供給されることを送信条件に含める。
- Annex-B の 3 / 4 バイト開始コードと任意位置で分割された TCP データを扱えるようにする。複数 NAL を含むアクセスユニットを正しく復元する方針を実証する。
- AUD の有無を確認する。AUD を送信条件に含める案と、映像構造から境界を解析する案を評価し、単純さと互換性に基づいて選ぶ。採用条件を検証結果とテストに固定する。
- MediaCodec の構成情報、アクセスユニット投入単位、表示順とタイムスタンプの扱いを、実際の FFmpeg 出力で確認する。生 H.264 に撮影時刻がない制約も記録する。
- 受信バッファ、未完 NAL、アクセスユニット、キュー、無通信時間の上限と超過時の明示的エラーを定める。過負荷時はセッションを終了して復旧させる方式から始め、任意の圧縮フレームを捨てて破損させない。

**成果物:** 再現可能な Android ビルド、映像境界処理と単体テスト、送受信の互換条件。

**完了条件:** 任意の TCP 分割・結合でも元のアクセスユニットを復元でき、上限超過や不正入力を有限時間・有限メモリで失敗させられる。両 PC の出力が同じ受信条件を満たす。H.264 ファイルが生成できただけでは完了にしない。

## P2: 最小の受信・デコード・表示

**前提:** P1 完了。対象: R02、R05〜R07、Q05、Q06。

作業:

- Surface が使用可能な前景状態で、検証済みの USB 側アドレスに待ち受けを開始する。
- 1 セッションを受け付け、P1 の映像処理から MediaCodec へ渡して描画する。受信・デコード待ちで UI を停止させない。
- SPS/PPS 等の構成情報と復旧可能な開始点を待ち、黒画面のまま成功扱いにしない。
- 低遅延機能の対応を照会し、対応する場合に有効化する。非対応の場合は状態を明示し、通常デコード経路を確認する。
- 全画面、向き固定、縦横比維持、表示中の点灯維持を実装する。
- 許可された環境ではエミュレーターを補助に使う。エミュレーターの adb 転送は開発専用であり、USB 経路の成立を示す証拠にしない。

**成果物:** 最小表示 APK、疎通結果。

**完了条件:** 2184×1968 の映像を連続表示でき、正しい画面・向き・縦横比を確認できる。少なくとも Fold 実機でデコード互換性を確認する。

## P3: 復旧・診断・資源管理

**前提:** P2 完了。対象: R04、R08、R09。

作業:

- 待機、接続中、構成情報待ち、表示中、エラーの状態とユーザーに必要な操作を画面へ表示する。
- バイト量からのビットレート、入力アクセスユニット数、表示出力数、アプリ内処理時間、低遅延機能の有効状態を区別して表示する。
- EOF、無通信、USB 切断、破損映像、デコードエラーでセッションを終了し、資源を解放する。接続が生きたまま映像だけ止まる場合も扱う。
- 2 本目の接続を明示的に拒否する。終了済みの処理が新セッションを壊さないようにする。
- バックグラウンド移行、画面消灯、Surface 再生成、アプリ終了時に停止・解放し、前景復帰後に再接続できるようにする。
- USB アドレス変更時は再確認と待ち受け再開を可能にする。点灯維持とソケット、スレッド、デコーダーを持ち越さない。

**成果物:** 診断・復旧を備えた APK、異常系とライフサイクルのテスト。

**完了条件:** adb / logcat なしで失敗理由と復旧方法が分かる。反復する切断・再接続と前景復帰で映像が戻り、メモリや資源が継続増加しない。

## P4: 両 PC と Fold 実機の結合・受け入れ

**前提:** P3 完了。対象: 全要求。

作業:

- 同一 APK を両 PC の USB テザリング経路で使い、開発者モード無効で開始・停止・再接続する。
- 検証計画の機能・異常系・アクセス範囲・ルーティング試験を実施する。
- 両 PC で 60fps を測定し、表示品質、総遅延、CPU / GPU 負荷、発熱、連続稼働を記録する。
- 未達の場合は取り込み・エンコード・転送・デコードを切り分けて改善する。30fps やソフトウェア経路の結果を 60fps / HW 経路の成功と混同しない。
- 実証できた FFmpeg コマンドだけを、対象環境とバージョン付きで運用文書に採録する。

**成果物:** 環境別の受け入れ結果と既知の制約、再現可能な送信条件。

**完了条件:** 全必須試験が成功し、性能基準を満たす。未合意の性能基準や未測定の項目が残る場合は、機能試作完了までとし、受け入れ完了にはしない。

## P5: 再現可能な個人運用への整理

**前提:** P4 完了。

作業:

- APK のビルド・署名・手動導入、起動、終了、再接続、既製ドライバー設定、ネットワーク設定の復元方法を運用文書へ反映する。
- 個人利用でも APK の更新に必要な署名鍵を管理する。鍵・資格情報・端末の識別情報をリポジトリへ含めない。
- バージョンと設定を固定し、別の作業日にも手順から再開できることを確認する。
- 採択した重要判断があれば ADR を追加し、現在設計と索引を同期する。

**成果物:** 再現可能な導入・運用文書、対応環境一覧。

**完了条件:** 開発者モードや記憶頼みの手作業に依存せず、文書に沿って両 PC から利用できる。不要な設定変更を残さず終了できる。

## 見積もりと打ち切り

P0・P1 の結果が出るまでは日数やコード行数を確約しません。管理ポリシー違反、USB 限定待ち受け不可、対象ディスプレイの取得不可、共通デコード条件の不成立は計画見直しの条件です。制約を黙って緩めたり、対象 PC を除外して完成扱いにしたりしません。
