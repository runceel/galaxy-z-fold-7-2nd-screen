# プロジェクトのドキュメント手順

常に守る規則は `AGENTS.md` にあります。このスキルは、その規則を具体的な作業に当てはめるときの手順です。

## 作業の振り分け

| やりたいこと | 手順 |
| --- | --- |
| 全体方針を決めた・変えた | [ADR](#adr) |
| 実機や環境で測定した | [検証結果](#検証結果) |
| コマンドや導入手順が動くと確認できた | [検証済み手順への昇格](#検証済み手順への昇格) |
| 新しい文書が必要か迷う | [文書を追加する条件](#文書を追加する条件) |
| 書いた内容の粒度を確認したい | [粒度の確認](#粒度の確認) |

## ADR

### 作成する条件

次の条件を複数満たす判断は ADR にします。

- 複数のコンポーネントや将来の実装を拘束する
- 信頼境界、責務境界、データの所有、ライフサイクルを変える
- 代替案との間に意味のあるトレードオフがある
- 後から覆すコストが高い
- 理由を知らない実装者が元に戻してしまう可能性がある

このプロジェクトで想定される例: 認証の導入、伝送形式の変更（Annex-B H.264 over TCP 以外）、待ち受けの方向の変更、バックグラウンド動作の追加、初期対象外の機能を対象に入れる。

局所的なリファクタリング、命名、既存設計内のバグ修正、1 か所で完結する最適化は ADR にしません。

### 手順

1. 判断の根拠となる事実（検証結果、制約、公式資料）を確認する。理由を確認できない場合は ADR を作らない。
2. `docs/adr/` がなければ作成し、[templates/adr.md](templates/adr.md) を元に `docs/adr/NNNN-short-slug.md` を追加する。番号は 0001 からの連番。
3. 採択前は Status を `Proposed` にする。ユーザーの合意を得てから `Accepted` にする。
4. 同じ変更の中で `docs/architecture.md` を現在形で更新する。経緯や廃止した案は書かない。要求や計画に影響があれば、それらも更新する。
5. `docs/adr/README.md` の索引（番号、タイトル、Status）に追加する。索引がなければ作成する。
6. 既存の判断を変える場合は、旧 ADR の本文を書き換えない。新しい ADR に `Supersedes` を書き、旧 ADR は `Status` と `Superseded by` だけを更新する。

ADR には判断の理由と得失を、アーキテクチャには現在従う規則だけを書きます。同じ説明を両方に書きません。

## 検証結果

1. [templates/validation-result.md](templates/validation-result.md) を元に `docs/validation-results/YYYY-MM-DD-<環境>-<段階>.md` を追加する。例: `2026-10-20-arm64-p0.md`。
2. 環境（OS、アーキテクチャ、GPU、ドライバー、FFmpeg、VDD、Fold の OS、アプリ版）を記録する。
3. 試験 ID ごとに、期待値、実測値、判定（成功・失敗・未確認）を記録する。試験できなかった項目は未確認とし、成功に含めない。
4. 30fps やソフトウェアエンコードで得た結果は、そのことを明記する。60fps や HW エンコードの達成として扱わない。
5. 結果によって計画や要求が変わる場合（未確定事項の解消、段階の完了、ブロッカーの発生）は、該当する文書を更新し、検証結果へリンクする。
6. 機密性のある画面、署名鍵、端末の識別情報、個人情報を含めない。

## 検証済み手順への昇格

引き継ぎメモや計画にあるコマンドは未検証です。`docs/operations.md` に確定手順として載せるのは、次をすべて満たしたものだけです。

- 対象環境で実際に実行し、その結果を検証結果に記録している
- 対象 PC、OS、ツールとドライバーのバージョン、前提条件を併記している
- 管理ポリシーの回避、ファイアウォールやセキュアブートの無効化を含まない
- 変更した設定を元に戻す方法がある

片方の PC でしか確認できていない手順は、対象 PC を明記し、もう一方を未確認と書きます。

## 文書を追加する条件

先回りして文書を増やしません。次のタイミングで追加します。

| 文書 | 追加するタイミング | 置き場所 |
| --- | --- | --- |
| ADR | 全体方針を採択・変更したとき | `docs/adr/` |
| 検証結果 | 実機や環境で測定したとき | `docs/validation-results/` |
| ビルド・導入手順 | Android プロジェクトと APK の生成・導入が実証できたとき | まず `docs/operations.md` に追記 |
| トラブルシューティング | 実際の障害と復旧方法を確認できたとき | まず `docs/operations.md` に追記 |

既存の文書が長くなり、読者や更新理由が明確に分かれたときだけ分割します。分割したら `AGENTS.md` の文書一覧と `README.md` の読む順序を更新します。

## 粒度の確認

書いた後に次を確認します。

- コードを読めば分かること（関数名、行番号、分岐、内部データ形式）が混ざっていないか
- 同じ説明が複数の文書にないか。あれば一方に寄せ、他方はリンクにする
- 未検証の想定や推測を、事実や確定事項として書いていないか
- 要求 ID、試験 ID、段階の参照とリンクが正しいか
- 引き継ぎメモを書き換えていないか
